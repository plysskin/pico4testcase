# Правила работы с Git — Test Case PICO 4 (U3D)

Документ фиксирует, как в этом репозитории ведутся ветки, коммиты, слияния и публикация.
Правила действуют для всех, кто коммитит в проект — человек и агент — и дополняют
[.gitignore](.gitignore). Документ живой: новая договорённость — правка сюда.

**Два главных правила:**

1. **Каждая задача — в отдельной ветке.** В `main` напрямую не коммитим.
2. **В `main` мерджим только по прямому указанию.** Подготовить ветку и сказать «готово» —
   можно; влить в `main` — только после явной команды.

---

## 1. Ветки

| Правило | Как |
|---|---|
| База | Ветка создаётся от актуального `main` (`git switch main` → `git pull --ff-only`) |
| Одна ветка — одна задача | Фикс, рефакторинг и новая фича — разные ветки, даже если правки рядом |
| Имя | `<тип>/<краткое-имя>`, латиница, kebab-case: `feature/virtual-button-panel` |
| Жизнь | От создания до мерджа; после мерджа ветка удаляется |
| Переиспользование | Ветку под другую задачу не переиспользуем — создаём новую |

Типы веток:

| Тип | Когда |
|---|---|
| `feature/` | новая функциональность и изменения поведения |
| `fix/` | исправление дефекта |
| `docs/` | документация (`architecture.md`, `problems-backlog.md`, этот файл) |
| `refactor/` | изменение структуры кода без изменения поведения |
| `chore/` | настройки проекта, пакеты, чистка мусора, сборка |
| `test/` | тесты и проверки |

Примеры: `feature/fov-anchored-buttons`, `fix/wmv-transcode`, `docs/git-workflow`,
`chore/remove-legacy-scene`.

Ветка с незавершённой работой в `main` не попадает: недоделанное живёт в ветке
и не мерджится, пока не готово. Правки самого этого файла — тоже отдельная ветка `docs/`.

---

## 2. Рабочий цикл

```bash
# 1. старт задачи от свежего main
git switch main
git pull --ff-only

# 2. своя ветка
git switch -c feature/virtual-button-panel

# 3. работа: правки → осмысленные коммиты
git status                     # глазами: что именно меняется
git diff                       # глазами: что именно уходит в коммит
git add Assets/Scripts/tcFovPanelAnchor.cs "Assets/Scenes/SampleScene 1.unity"
git commit -m "feat: панель кнопок привязана к полю зрения"

# 4. публикация ветки
git push -u origin feature/virtual-button-panel

# 5. мердж в main — только по прямому указанию (см. раздел 6)
```

`git add -A` и `git add .` без просмотра `git status` не используем: в проекте так уже
попадали в коммит служебные файлы (`.harness-unity-bridge/`, локальные бэкапы сцены).
Пути перечисляем явно.

---

## 3. Коммиты

- **Атомарность.** Один коммит — одна причина изменения. Если правка затрагивает несвязанное
  (фикс + рефакторинг), это два коммита, при необходимости — две ветки.
- **Сообщение:** `тип: краткое описание` (тип — латиницей, описание — по-русски или
  по-английски, но единообразно в рамках ветки).
  В теле — **зачем** сделано и что проверено, а не пересказ диффа.

  ```
  fix: видео .wmv не воспроизводится на PICO 4

  Android-бэкенд VideoPlayer не поддерживает VC-1/WMV. Клипы перекодированы
  в H.264/AAC, имена ассетов сохранены. Проверено в Play Mode и на шлеме.
  ```

- **Что попало в коммит — то и проверено.** Коммит не должен содержать закомментированный
  код, отладочные `Debug.Log` «на время» и временные файлы, если это не оговорено явно.
- **Незавершённое** — в отдельный коммит с явной пометкой (`wip:`) или в stash, но не
  в `main`.
- Коммит после мерджа не переписываем: `git revert`, а не `git reset`/`--amend`.

---

## 4. Что не коммитим

| Путь / тип | Почему |
|---|---|
| `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `MemoryCaptures/` | генерирует Unity, в git не нужны |
| `*.csproj`, `*.sln` | генерируются Unity из `.asmdef` |
| `Build/`, `Builds/`, `*.apk`, `*.aab`, `*.unitypackage` | артефакты сборки |
| `*.keystore`, `*.jks`, пароли и alias | секреты; хранятся вне репозитория |
| `.harness-unity-bridge/` | runtime-файлы моста агента |
| `.scene-backup/`, `*.bak`, `*~` | локальные страховочные копии |
| `.vs/`, `.idea/`, `.vscode/` (кроме общих файлов) | настройки IDE |

Появился новый тип временных файлов — **сразу строка в `.gitignore`**, а не разовый
коммит «потом уберём». Проверка перед коммитом: `git status` не должен показывать
среди изменений ничего служебного.

Обратное правило тоже важно: **`*.meta` коммитим всегда** (см. раздел 5) — это не мусор,
а часть ассета.

---

## 5. Unity-специфика

- **`.meta` — вместе с ассетом.** Добавили/переименовали/удалили файл в `Assets/` — в том же
  коммите и его `.meta`. Ассет без `.meta` ломает ссылки в сценах и префабах.
- **Сцены и префабы — текстовый YAML.** Это позволяет дифф, но **конфликт сцены не склеиваем
  вручную вслепую**: выбираем одну сторону, открываем сцену в Unity и переносим нужные правки.
  Если правка сцены делается руками (вне редактора) — после неё обязательно открыть проект
  и проверить, что сцена грузится без ошибок.
- **Не пересохраняем сцену/префабы «на всякий случай»**: лишние изменения GUID/порядка
  компонентов создают шум и конфликты.
- **Одну сцену не редактируем параллельно в двух ветках.** Правки сцены — атомарно с кодом,
  который их использует (компонент + его поля в сцене — один коммит).
- **Бинарные ассеты** (`.exr`, `.wmv`, `.png`, `.ttf`, `RenderTexture`) не мерджатся:
  при конфликте осознанно выбирается одна версия. Крупные бинарники добавляем только
  по необходимости — размер сборки уже отмечен в [problems-backlog.md](problems-backlog.md).
- **Проверка перед коммитом:** консоль Unity без ошибок компиляции, сцена открывается,
  в Build Settings индексом 0 стоит `Assets/Scenes/SampleScene 1.unity`.

## 6. `main` и мердж

- **Условие мерджа — прямое указание** («мерджи», «вливай в main», «можно в main»).
  Без него ветка остаётся веткой, даже если всё готово и проверено.
- **Порядок мерджа:**

  ```bash
  git switch main
  git pull --ff-only origin main
  git merge --no-ff feature/virtual-button-panel
  # проверка: проект компилируется, сцена играется
  git push origin main
  git branch -d feature/virtual-button-panel
  git push origin --delete feature/virtual-button-panel
  ```

- **`--no-ff`** — чтобы в истории было видно, что это была отдельная задача.
- Конфликты решаются **в ветке**, до мерджа, а не в `main`.
- Инициатива: подготовил ветку → запушил → сообщил «готово к мерджу». Сам не мерджу.
- `main` не ребейзим и не переписываем. Rebase допустим только для своей feature-ветки,
  до пуша и до мерджа.

## 7. Remote

| Remote | URL | Роль |
|---|---|---|
| `origin` | `github.com/plysskin/pico4testcase` | основной, пуш по умолчанию |
| `Gitlab` | `gitlab.dev.inbisyst.ru/piko-3d/piko1` | зеркало |

- Пуш — в `origin` (своя ветка). В `Gitlab` — по указанию, для синхронизации.
- **В `main` напрямую не пушим** — только результат мерджа (раздел 6).
- **Force-push:** только своя ветка, только `--force-with-lease`; в `main` — никогда.

---

## 8. Аварийные ситуации

| Ситуация | Что делать |
|---|---|
| Правки не туда попали, ещё не закоммичено | `git restore <файл>`, `git stash` |
| Коммит не тот, ещё не запушен | `git reset --soft HEAD~1` и пересобрать коммит |
| Коммит уже запушен | `git revert <sha>` — не переписывать историю |
| Случайно удалил ветку/коммит | `git reflog` → `git switch -c <ветка> <sha>` |
| Испортил сцену | восстановить из `git` (`git restore`), локальные бэкапы — во временной папке, не в репозитории |

## 9. Чек-лист

**Перед коммитом**

- [ ] Ветка своя и создана от актуального `main`
- [ ] В коммите только файлы этой задачи (`git status`, `git diff` просмотрены)
- [ ] Нет служебных файлов из раздела 4
- [ ] `.meta` на месте для всех добавленных/удалённых ассетов
- [ ] Консоль Unity без ошибок

**Перед пушем**

- [ ] Коммиты атомарные и с понятными сообщениями
- [ ] Пуш в свою ветку, не в `main`
- [ ] Секретов (keystore, пароли) в диффе нет

**Перед мерджем в `main`**

- [ ] Есть прямое указание на мердж
- [ ] `main` обновлён (`git pull --ff-only`)
- [ ] Проект проверен в редакторе: компиляция, сцена в Build Settings, Play Mode
- [ ] После мерджа: `git push origin main`, ветка удалена
